# Deploying the Team Hub API (Render + Neon, free tiers)

## Security design

| Layer | Control |
|---|---|
| Database logins | `teamhub_migrator` owns the tables and is used only by `alembic upgrade head` at start-up. `teamhub_app` (the running API) can only read and write rows: it cannot create, alter or drop tables, and has a 10-connection cap |
| Audit trail | A PostgreSQL trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` on `audit_log` for every user. The app login also has those privileges revoked. CI proves the trigger after every migration (`scripts/check_db_guards.py`) |
| Transport | Every database URL must use `sslmode=require` (production refuses to start otherwise); the setup script adds `channel_binding=require`. HTTPS only on Render, HSTS in production |
| Timeouts | App login: `statement_timeout` 15 s, `lock_timeout` 5 s, `idle_in_transaction_session_timeout` 60 s. Pool of 5 (+2), recycled every 4 minutes, before Neon suspends idle compute |
| Isolation | The database `teamhub` refuses connections from anyone else (`REVOKE ALL … FROM PUBLIC`), and nobody else can create objects in its schema |
| Secrets | Generated by `scripts/neon_setup.py` into a file only the founder's Windows account can read, sent to Render through its API, never printed, never committed. Bank details, the SMTP password and the signature are entered by the founder in the Render dashboard |
| Personal data | Banking and ID details are encrypted in the application (Fernet) before they reach the database. **Back up `FIELD_ENCRYPTION_KEY` in the password manager**: without it those fields cannot be read |
| Start-up | In production the API refuses to start without strong secrets, PostgreSQL over TLS, SMTP, an admin notification address and the signature |

Data location: Neon `aws-eu-central-1` (Frankfurt) and Render Frankfurt. Personal information leaves South Africa for the EU, which has data-protection law at least as strong as POPIA (POPIA section 72). Mention this in the privacy notice.

## Steps

1. **Neon:** create the project `saxs-team-hub` (PostgreSQL 17, AWS Europe Central / Frankfurt). Copy the owner connection string (*Connection pooling* off) into a private file as `DATABASE_URL=…`.
2. **Database setup** (from `backend/`):
   `python -m scripts.neon_setup <owner-file> <render-env-file>`
   This creates the database, the two logins and the secrets.
3. **Render:** create the web service from `render.yaml` and set the generated values (`DATABASE_URL`, `MIGRATION_DATABASE_URL`, `SECRET_KEY`, `FIELD_ENCRYPTION_KEY`, `JOBS_TOKEN`) plus `FRONTEND_URL`/`CORS_ORIGINS` (the service's own URL until the frontend exists).
4. **Founder, in the Render dashboard:** `SMTP_USER`, `SMTP_PASS`, `ADMIN_NOTIFY_EMAIL`, `SIGNATORY_NAME`, the Secret File `signature.png`, and the five `COMPANY_BANK_*` values.
5. **Deploy.** Start-up runs the migrations as `teamhub_migrator`.
6. **Lock the audit log for the app login:**
   `python -m scripts.neon_setup <owner-file> <render-env-file> --after-migrate`
7. **Check:** `GET /api/health` returns 200 with `database`, `email` and `signature` all true; run `python -m scripts.check_db_guards` with `DATABASE_URL` set to the migrator URL.
8. **First admin:** the founder runs `python -m app.cli create-admin admin@saxsprojects.co.za` on their own computer with `DATABASE_URL` set to the app URL (it asks for the password privately), then switches on two-factor straight away.

## Backups

Neon's free plan keeps a short restore window (point-in-time restore of recent history). For records that must be kept for years (invoices, payouts, signed acceptances), also take a regular `pg_dump` with the migrator URL and keep it encrypted off-site.
