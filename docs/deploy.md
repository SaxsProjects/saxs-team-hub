# Deploying the Team Hub API (Render + Neon, free tiers)

## Security design

| Layer | Control |
|---|---|
| Database logins | `teamhub_migrator` owns the tables and is used only by `alembic upgrade head` at start-up. `teamhub_app` (the running API) can only read and write rows: it cannot create, alter or drop tables, and has a 10-connection cap |
| Audit trail | A PostgreSQL trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` on `audit_log` for every user. The app login also has those privileges revoked. CI proves the trigger after every migration (`scripts/check_db_guards.py`) |
| Transport | Every database URL must use `sslmode=require` (production refuses to start otherwise); the setup script adds `channel_binding=require`. HTTPS only on Render, HSTS in production |
| Timeouts | App login: `statement_timeout` 15 s, `lock_timeout` 5 s, `idle_in_transaction_session_timeout` 60 s. Pool of 5 (+2), recycled every 4 minutes, before Neon suspends idle compute |
| Isolation | The database `teamhub` refuses connections from anyone else (`REVOKE ALL … FROM PUBLIC`), and nobody else can create objects in its schema |
| Secrets | Generated by `scripts/neon_setup.py` into a file only the founder's Windows account can read, sent to Render through its API, never printed, never committed. Bank details, the SMTP password and the signature are entered by the founder in the Render dashboard |
| Personal data | Banking and ID details are encrypted in the application (Fernet) before they reach the database. **Back up `FIELD_ENCRYPTION_KEY` in the password manager**: without it those fields cannot be read |
| Start-up | In production the API refuses to start without strong secrets, PostgreSQL over TLS, SMTP, an admin notification address and the signature |

Data location: Neon `aws-eu-central-1` (Frankfurt) and Render Frankfurt. Personal information leaves South Africa for the EU, which has data-protection law at least as strong as POPIA (POPIA section 72). Mention this in the privacy notice.

## Steps

1. **Neon:** create the project `saxs-team-hub` (PostgreSQL 17, AWS Europe Central / Frankfurt). Copy the owner connection string (*Connection pooling* off) into a private file as `DATABASE_URL=…`.
2. **Database setup** (from `backend/`):
   `python -m scripts.neon_setup <owner-file> <render-env-file>`
   This creates the database, the two logins and the secrets.
3. **Render:** create the web service from `render.yaml` and set the generated values (`DATABASE_URL`, `MIGRATION_DATABASE_URL`, `SECRET_KEY`, `FIELD_ENCRYPTION_KEY`, `JOBS_TOKEN`) plus `FRONTEND_URL`/`CORS_ORIGINS` (the service's own URL until the frontend exists).
4. **Founder, in the Render dashboard:** `RESEND_API_KEY` (a Resend key with *sending access* only, for the verified domain saxsprojects.co.za), `SMTP_FROM` = `admin@saxsprojects.co.za`, `ADMIN_NOTIFY_EMAIL`, `SIGNATORY_NAME`, `SIGNATURE_IMAGE_BASE64` (the signature PNG as base64; Render's Secret Files are meant for text) and the five `COMPANY_BANK_*` values.
   Render's free plan blocks outgoing SMTP ports (25, 465, 587), so email is sent over HTTPS through Resend (free: 3,000 a month, 100 a day). Resend's DNS records (DKIM `resend._domainkey`, and MX + SPF on the `send` subdomain) live in Vercel DNS next to Zoho's; they do not affect Zoho mail. Zoho SMTP (`SMTP_USER`, `SMTP_PASS`) is only used when `RESEND_API_KEY` is empty. Test with `python -m app.cli check-email`.
5. **Deploy.** Start-up runs the migrations as `teamhub_migrator`.
6. **Lock the audit log for the app login:**
   `python -m scripts.neon_setup <owner-file> <render-env-file> --after-migrate`
7. **Check:** `GET /api/health` returns 200 with `database`, `email` and `signature` all true; run `python -m scripts.check_db_guards` with `DATABASE_URL` set to the migrator URL.
8. **First admin:** the founder runs `python -m app.cli create-admin admin@saxsprojects.co.za` on their own computer with `DATABASE_URL` set to the app URL (it asks for the password privately), then switches on two-factor straight away.

## Backups

Backups run on their own, using the read-only `teamhub_backup` login (it can read every table and change nothing):

| Where | When | Kept |
|---|---|---|
| GitHub Actions (`.github/workflows/backup.yml`), as a private artifact | Sundays 02:30 SAST | 90 days |
| The founder's laptop: Task Scheduler task "SaxsProjects Team Hub backup" running `backend/scripts/local_backup.ps1` into `%USERPROFILE%\.saxs-team-hubackups` (log: `backup.log`) | Sundays 10:00, or the next time the laptop is on | Forever |

The cloud backup needs two repository secrets, `TEAM_HUB_BACKUP_DATABASE_URL` and `TEAM_HUB_BACKUP_KEY` (values in `.saxs-team-hub\github-secrets.env`). GitHub emails the owner if a scheduled run fails. Files are gzip JSON encrypted and authenticated with Fernet; the personal fields inside are encrypted again with `FIELD_ENCRYPTION_KEY`. **Keep `BACKUP_KEY` and `FIELD_ENCRYPTION_KEY` in Bitwarden** — without them backups cannot be read.

Manual backup or check: `python -m scripts.backup backup FILE` / `verify FILE`.
To restore: create an empty database, `alembic upgrade` it to the revision `verify` shows, then `python -m scripts.backup restore FILE`. CI rehearses this on PostgreSQL on every change.

## Web app sign-ins

The web app (`frontend/`, on Vercel at `hub.saxsprojects.co.za`) keeps people signed in while they work:

- A 15-minute access pass (`ACCESS_TOKEN_MINUTES`) is held in memory only.
- An HttpOnly, Secure, SameSite=Strict renewal cookie (`__Host-teamhub_session`) is swapped for a new one on every renewal; reusing an old one ends the session (`app/sessions.py`).
- Sign-ins end after 30 minutes without activity (`SESSION_IDLE_MINUTES`), after 12 hours for team members (`SESSION_MAX_HOURS`) or 8 hours for the founder (`ADMIN_SESSION_MAX_HOURS`), on sign-out, and on any password change or reset.

### Trusted devices (stay signed in on your phone)

"Keep me signed in on this device" (ticked by default on phones and in the apps) trusts the device after a full
sign-in with password and two-factor code. A second HttpOnly cookie (`__Host-teamhub_device`, 90 days, renewed on
every unlock) names the device; only its hash is stored (`trusted_devices`, `app/devices.py`).

- When a sign-in ends, the trusted device shows **Welcome back** with the email filled in. It unlocks with a passkey
  (Face ID on iPhone, fingerprint or face on Android, Windows Hello on Windows) or the password alone. No code.
- The app locks after 5 minutes in the background.
- Two-factor is asked only on a new device and when resetting a forgotten password.
- Trust ends when the device is removed (Settings > Security), after a password reset (every device), after
  90 days unused (`DEVICE_TRUST_DAYS`), after 5 wrong passwords on it (`DEVICE_UNLOCK_FAILURES`), or when the
  account is switched off. A new trusted device sends an email alert.
- Passkeys: only the public key is stored (`passkeys`). The relying party is the first `CORS_ORIGINS` host
  (`hub.saxsprojects.co.za`; override with `WEBAUTHN_RP_ID`). The Android app's signing certificate is in
  `ANDROID_SIGNING_CERT_SHA256` (public; it is in every APK) and in `frontend/public/.well-known/assetlinks.json`.
  If the Android signing key ever changes, update both.
- iPhone: open the hub in Safari, Share > Add to Home Screen. Face ID works through passkeys; no App Store app needed.
  Safari may forget the device cookie after 7 days without opening the app; then the full sign-in is asked once.

The cookie only reaches the API when the app and API share the company domain, so the API must be served at
**`api.saxsprojects.co.za`** (a Render custom domain, free) and the app at **`hub.saxsprojects.co.za`**:

1. Render → service → Settings → Custom Domains → add `api.saxsprojects.co.za`.
2. Vercel DNS for saxsprojects.co.za → CNAME `api` → the `onrender.com` host Render shows.
3. Render environment: `CORS_ORIGINS=https://hub.saxsprojects.co.za` and `FRONTEND_URL=https://api.saxsprojects.co.za`.
4. Vercel project with root directory `frontend/`, domain `hub.saxsprojects.co.za`.
